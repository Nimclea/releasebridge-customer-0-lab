# 场景条件怎么产生，而不伪造结果

该仓库不是一个“输入 R04 就打印 UNKNOWN”的模拟器。
真正裁决只能来自正在测试的 ReleaseBridge。

- R04：使用真实尚未完成的必要 Check。初次建库不配置人为阻塞的 Required Check；
  进入该轮时只在测试范围内设置证据完成时序，不改产品裁决。
- R05：两种舍入都有可执行样例，当前客户业务规则没有选择。允许先“稍后”再选择，
  必须保留同一个 Case；支持两种算法的测试通过不等于客户已选择。
- R06：创建 A 的真实 Run，再产生 B，测试旧证据不冒用到 B。禁止手工改写 Run 内容。
- R07：先识别需要扩权，不先越权再把已发生的违规解释成未知。真正批准后再修改。
- R08：在实验 Candidate 中引入已知 R01 行为回归，只用于拒绝测试；保护状态不手工撤销。
- R09：在实验 Candidate 中改动 policies/restricted-settings.json 的实验字段；不碰真 Token。
- R10：用不完整的真实修复让重复 SKU 断言失败，不把网络故障当业务反证。
- R11：重复 id 同金额通过但不同金额不拒绝，反证作为独立失败输入交回原 Agent。
- R12：使用有效但属于另一个 Candidate 的证据引用，测试实际消费者拒绝错绑。
  这是受控的错误输入，不是冒充真实签名。不自动重试、不更换身份绕过。

最小验收不是“所有失败自动重试直到绿灯”。每轮必须有可执行 NEXT，并保留此前保护。
当前产品无法接收某类证据时，状态是 BLOCKED/NOT_TESTABLE，不是已通过安全验收。
